# Sakurai-Skills

**言語:** [English](README.md) | 日本語

ゲームデザイン、実装計画、レビュー、制作進行、プレゼンテーションに使える、エージェント向けのタスク別Skills集です。桜井政博氏の公開ゲーム制作動画を参考に作成した中間ノートを、出典の層を追跡できる知識ベースと実用的なレビュー手順に整理しています。

## 参照元と作成方法

参照元は[桜井政博氏のYouTubeチャンネル](https://www.youtube.com/@sora_sakurai_jp)です。対象範囲は[「まとめ動画」再生リスト](https://www.youtube.com/playlist?list=PLi8SA3sbzYVQb8vloj23961McKcnihGVx)に含まれる動画のうち、「雑談」を除く全まとめ動画です。資料を作成する際、Geminiにこれらの動画を参照させたうえで、構造化ノートを本リポジトリ向けに整理しました。

桜井氏本人や公式見解を代弁するものではありません。リポジトリに収録された資料はAI Studioで構造化した中間ノートであり、動画の逐語録や検証済みの書き起こしではありません。各SOURCE項目は、元動画と照合するまでは二次要約として扱います。

## 出典の層

知識を利用するときは、次の3層を区別してください。

- **SOURCE**: 提供された中間ノートが明示的な発言・内容として記録したもの。動画との照合は未実施です。
- **GENERALIZED**: ノート内の内容から導いたデザイン上の抽象化。
- **AGENT**: AIエージェント向けの作業手順、技術的な適用、解釈。

原則は状況に応じて使う判断材料です。プレイヤー、ジャンル、開発段階、プラットフォーム、制約、根拠、依頼範囲を踏まえて選び、異なる原則間の緊張関係を単一の標語で解消しないでください。

## 候補から原則への整理

資料14件を `sources/raw/` に保持し、`sources/index.yaml` にハッシュ付きで記録しています。そのうち知識資料13件から、構造化された候補IDを177件収録しています。

すべての候補に `sources/candidate-mapping.yaml` で処遇と対応する原則を記録しています。詳細な抽出データは `principles/catalog.json`、閲覧用の個別記録は `principles/derived/` にあります。対応表には元ID・タイトル、保持・除外した情報、忠実度の評価を記録しています。横断的な統合原則17件も別途保持しており、索引上の原則は合計194件です。候補数や資料カテゴリ別の内訳は `reports/candidate-coverage.md` を参照してください。

## 構成

| パス | 内容 |
|---|---|
| `sources/raw/`, `sources/index.yaml` | 元資料と出典情報 |
| `sources/candidate-index.yaml` | 候補一覧 |
| `sources/candidate-mapping.yaml` | 候補ごとの処遇と原則への対応 |
| `principles/catalog.json` | 出典層を分けた機械可読の原則データ |
| `principles/` | 人が読める原則記録と横断的な統合 |
| `rules/principle-graph.yaml` | 意味クラスタ、型付きリンク、状況別に整理した原則間の緊張関係 |
| `rules/lint-rules.yaml` | 自動判定ではなくレビュー補助として使う観点 |
| `rules/anti-patterns.yaml` | 症状、関連原則、誤検知しうる例、確認質問 |
| `skills/` | ルーターと統合レビューを含む24個のタスク別Skills |
| `workflows/`, `checklists/` | 開発手順と段階・領域別の確認項目 |
| `schemas/`, `scripts/` | データ契約、生成、検証スクリプト |
| `tests/`, `reports/` | 文脈別の回帰ケース、サンプルプロジェクト、網羅性・忠実度の監査 |

元動画のカテゴリは出典ラベルです。ゲームプレイ、UI、音声、チーム、技術実装などの意味クラスタを使い、関連するタスクSkillsへ知識を案内します。

## 使い方（クイックスタート）

1. ゲームのリポジトリと本リポジトリの両方を、エージェントから参照できるようにします。Skillsが原則・チェックリストを開けるよう、本リポジトリへのアクセスを保ってください。
2. 依頼の最初に `skills/sakurai-game-dev/SKILL.md` を使うよう指定します。ルーターがタスクに合う領域別Skillと知識記録を選びます。
3. ゲーム全体を広くレビューする場合は、`skills/sakurai-review/SKILL.md` を使うよう指定します。
4. 何を調べるか、エージェントが何にアクセスできないかを伝えます。確認できた事実と推測を分け、ビルドやプレイテストが必要な点を明示するよう頼みます。

依頼には、必要に応じて次の情報を含めてください。

- **タスク:** 判断したいこと、機能、問題。
- **ゲームの前提:** ジャンル、対象プレイヤー、プラットフォーム、開発段階。
- **根拠:** 確認してほしいファイル、スクリーンショット、プレイテスト記録、ビルド。
- **制約:** 締め切り、チーム規模、性能目標、アクセシビリティ要件、スコープ。
- **成果物:** 希望する形式と詳しさ。

以下の依頼文をコピーして調整できます。

> `skills/sakurai-game-dev/SKILL.md` を使い、**[ゲーム／プロジェクト]** の **[機能または相談内容]** をレビューしてください。**[対象プレイヤー]** 向けの **[ジャンル]** で、プラットフォームは **[機種]**、開発段階は **[段階]** です。**[コード、ビルド、画像、プレイテスト記録など]** を確認してください。制約は **[制約]** です。指摘を優先度順に並べ、根拠、状況、トレードオフ、良い点を示してください。提供資料から確認できないことには、確認方法も添えてください。

記入例: 「ルーターSkillを使い、初心者向けモバイルプラットフォーマーのジャンプをレビューしてください。操作コードとプレイテスト記録を確認してください。考えられる問題を挙げ、操作タイミングや感触などビルド確認が必要なことは、未確認として明示してください。」

Skillsは、コンセプトとコアループ、ゲームプレイ・操作・難易度・レベル進行、プロトタイプ・導入、UI/UX・ゲームフィール、視認性・アニメーション・カメラ／エフェクト・音声、仕様・制作・チーム・スコープ、仕上げ・性能・マーケティング／プレゼンテーションを扱います。各Skillの `SKILL.md` に、使う場面、必要な根拠、レビュー手順、出力形式があります。

エージェントに導入する場合は、`skills/` をそのエージェントのSkills用ディレクトリにコピーするか、本リポジトリを読み取り専用資料として利用可能にします。各Skillは原則、チェックリスト、ワークフロー、元資料へのリンクを参照するため、可能ならリポジトリ全体にアクセスできるようにしてください。エージェントがSkillを自動検出しない場合は、上記ルーターのパスを明示して読み込ませてください。

## 検証と変更への協力

構造化された元資料を変更した場合は、`scripts/build-candidate-catalog.ps1`、`scripts/build-reports.ps1`、`tests/run-tests.ps1`、`scripts/validate.ps1` の順で実行します。元資料との対応を更新せずに、生成される候補記録だけを手編集しないでください。Skillsや原則記録を編集するときは出典の層を保ち、グラフと網羅性の対応を更新し、挙動に影響する変更には回帰ケースを追加してください。

## 制約

- チャンネルと再生リストは上記のとおり示していますが、提供資料には個々の主張に対応する動画URL、タイムスタンプ、逐語録が含まれていません。正確な引用や出典忠実度の確認には元動画との照合が必要です。
- 候補によって記録の詳しさに差があります。明示的なSOURCE情報がない場合、引用を作り出さず、確信度を低く記録して元資料を参照先にしています。
- E2E・文脈テストは架空の入力でルーターの選択と根拠の扱いを確認するもので、ゲームそのものをテストしたり、商用製品への有効性を証明したりするものではありません。
- YAMLの参照確認はリポジトリ固有の構造検証です。バリデーターはJSONスキーマの構文とカタログの契約項目を確認しますが、汎用JSON Schema/YAMLエンジンではありません。
