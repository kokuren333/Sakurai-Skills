# 不満・違和感の即時表明と『ダメ出し＋改善案』のセット提示

## Summary
問題に気づいたら後出しせずその場で表明し、ダメ出しには必ず具体的な改善案をセットで添える。

## SOURCE
仕事が終わった後やプロジェクト完了後に『実はこう思っていた』と後出しすることは厳禁。自尊心が満たされるだけで現場を疲弊させる。開発中なら修正可能であるため、気づいた瞬間に表明し、単に否定するのではなく『こうしたら良いのではないか』という改善案を必ずセットで提示する。

## GENERALIZED
批判的フィードバック（Critique）は発生タイミングが早いほど修正コストが指数関数的に下がる。否定（Reject）と代替案（Proposal）を不可分にすることで、議論を非難から建設的ソリューションへと誘導する。

## AGENT
AIコードレビューや設計レビューにおいて、単なる警告やリジェクト理由の出力にとどまらず、必ず修正コード差分（Patch）や代替アーキテクチャ案を併記するプロンプト設計に直結する。

## Why it matters
後出しの批判は誰も得をせずプロジェクトの遅延と不信感を生む。開発中の早期フィードバックと対案提示により、手早い軌道修正が可能となり、プレイヤー体験の向上に直結する。

## Use with context
- Domains: Code Review, Design Review, Team Collaboration
- Phases: Planning, Production, Alpha, Beta
- Trigger: コードレビュー実行時、または企画仕様書の検証時

## Agent questions
- 指摘事項に対して、具体的なコード例やパラメータ変更案が提示されているか？
- 問題の指摘がタイムリー（コミット直後）に行われているか？

## Suggested actions
- 指摘内容に『Issue』『Rationale』『Suggested Fix (Code/Config)』の3要素を含める。
- 懸念点を発見した場合、PRマージを待たずに即時ドラフトコメントまたはIssueとして起票する。

## Review criteria
- 改善案を含まないネガティブ指摘が存在しないこと。
- 指摘を受けた側が即座に次のアクションを取れる具体性があること。

## Anti-patterns
- スプリント終了後やQAフェーズに入ってから『最初からこうすべきだと思っていた』と口出しする（後出しジャンケン）。
- 『このUIは使いにくい』『このコードは汚い』とだけ指摘し、どう直すべきかを一切提示しない。
