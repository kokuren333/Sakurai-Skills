# 10人チームは7人分：組織拡大に伴う管理コストの織り込みと視座の引き上げ

## Summary
チーム規模拡大時にはマネジメント工数による実効作業量の目減りを織り込み、定期発表会で作業者の視座を俯瞰へと引き上げる。

## SOURCE
開発チームが10人になっても10人分の作業量にはならず、実質約7人分程度になる。マネジメント（方向性管理、スケジュール管理、ルール遵守、機材調達、意思疎通）にリソースが割かれるためである。また、優秀な職人がリーダー業務に回ると制作量が落ちる。対策として数ヶ月に一度の『成果物発表会』を開き、各自にプレゼンさせることで製造的視点から俯瞰した視点へと引き上げる。

## GENERALIZED
ブルックスの法則（人月の神話）の通り、組織スケールに伴うコミュニケーションオーバーヘッドは不可避である。管理コストをバッファとして織り込みつつ、定期的なデモ/ショーケースを通じて各個人のオーナーシップと全体最適の意識を維持する。

## AGENT
マルチエージェントシステムにおいても、エージェント数の増加に伴いオーケストレーションやコンフリクト調停のトークン消費・レイテンシが増大する。統括エージェントの負荷と各サブエージェントの自己評価機能を設計する際の指針となる。

## Why it matters
人数＝生産能力と単純計算すると確実に納期が破綻する。また、細分化された作業に没頭するメンバーが全体のゲーム体験を見失うと、局所最適化された質の低いパーツの集合体になってしまう。

## Use with context
- Domains: Project Planning, Resource Allocation, Team Management
- Phases: Production, Milestone Review
- Trigger: マイルストーン計画策定時、またはチームリソース計算時

## Agent questions
- タスク見積もりにコミュニケーション・レビュー・調整工数のマージン（約30%）が含まれているか？
- 各サブタスクの成果を統合して実機検証するスプリントレビュー/デモ機会が定義されているか？

## Suggested actions
- リソース計算時に `Effective_Capacity = Headcount * 0.7` 換算でスケジュールを試算する。
- 定期的なデモビルドの作成と、全モジュール統合テストのタイムボックスをスケジュールに組み込む。

## Review criteria
- リード職のタスクリストが自ら実装するタスクだけで100%埋まっていないこと。
- 結合デモのフェーズが定期的に配置されていること。

## Anti-patterns
- 人数を1.5倍に増やしたからといって、実装スピードも1.5倍になると仮定したマイルストーン設定。
- 分業体制の末端にいるスタッフが、完成した自作アセットがゲーム内でどう使われているかを知らない状態。
