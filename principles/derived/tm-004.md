# 関係職種全員同席による監修と意図の全体共有

## Summary
仕様や表現の監修・指示出しは、プランナー経由の伝言ゲームにせず、関係する全職種を同席させて大画面で直接行う。

## SOURCE
新・光神話パルテナの鏡では、ディレクターが企画に伝え、企画がプログラマーに伝える伝言ゲームにより、解釈が180度違うものが上がってくる反省があった。そのためスマブラfor以降は、大画面モニターの周りに関係者（企画、プログラム、モデル、モーション、エフェクト、サウンド等の担当者やリーダー）を30〜50人集め、実機画面を投影しながらマイクで指示出しし、全員で同時に監修内容と意図を聞く体制を敷いた。

## GENERALIZED
一次情報（ディレクターの意図やフィードバック）を関係者全員に同期的に浴びせることで、文脈の脱落・歪曲を防ぐ。他人が受けている指導を見聞きすること自体が、チーム全体のナレッジベース拡充と品質基準の均一化に寄与する。

## AGENT
分散開発環境では、Issueのコメント欄や非同期チャットで断片的に修正を指示するのではなく、画面共有を用いたオープンな公開レビュー会（録画アーカイブ付き）を実施することに相当する。

## Why it matters
伝言による意図の歪みは、再修正とスケジュール遅延の最大の原因となる。全員が『なぜその修正が必要なのか』の文脈を理解することで、以降の作業で自律的な判断が可能になる。

## Use with context
- Domains: Supervision, Quality Assurance, Requirement Engineering
- Phases: Production, Feature Implementation
- Trigger: コアゲームプレイ機能・アセットの仕様確定時および受け入れテスト時

## Agent questions
- 仕様変更の要求に、背景となるゲームデザイン上の意図（Why）が明記されているか？
- 関連する全モジュール（描画、挙動、音響、UI）への影響と指示内容が単一のコンテキストで共有されているか？

## Suggested actions
- ディレクション指示をチケット化する際、単一の担当者宛ではなく関連コンポーネントの全オーナをCC/レビュアーに含める。
- 修正要求に『ゲームデザイン上の意図』『期待される挙動』『関連アセットへの波及影響』のセクションを必須化する。

## Review criteria
- 指示内容が『AをBに変えて』という結果だけでなく『Cというプレイ感を実現するためにAをBに変える』という文脈を含んでいること。

## Anti-patterns
- ディレクター → 企画 → プログラマー → アーティスト という縦割り伝言チェーンでの指示伝達。
- 修正指示の背景や意図（Why）を伏せて、タスクのToDo（What）だけをチケットで投げる。
