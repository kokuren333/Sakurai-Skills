# Concept to prototype
1. State target player, fantasy, core loop, and constraints.
2. Name the riskiest assumption and evidence that would change the decision.
3. Build the smallest representative loop with low-cost assets.
4. Observe intended players performing a concrete task.
5. Separate observations from interpretations and record uncertainty.
6. Choose a next change or stop; preserve direction only while evidence supports it.

# Design change decision
1. Describe the player-facing problem with an example.
2. Identify affected systems, owners, schedule, and dependencies.
3. Check alignment with the core concept and relevant player evidence.
4. Compare change cost with the cost and impact of leaving the problem.
5. Name competing principles and the context that resolves the tension.
6. Assign a decision owner, record rationale, and choose low-cost validation.

# Playtest feedback review
1. Record build, audience, task, and test context.
2. Capture observed behavior separately from player language and team interpretation.
3. Group repeated observations without erasing outliers or accessibility needs.
4. Select an important uncertainty that can be tested next.
5. Specify change, comparison method, and owner.

# Polish pass
1. Review a representative build and capture evidence for each issue.
2. Prioritize impact, confidence, reach, and cost; do not inflate severity.
3. Check readability across camera distance, background, audio mix, and concurrent events.
4. Make bounded adjustments and compare before/after.
5. Record regressions and accessibility impacts.

# Pre-release review
1. Review scope, platform requirements, accessibility, performance, and known issues.
2. Verify public claims against the release candidate.
3. Verify backup, rollback, security, and incident procedures independently.
4. Assign owners to blockers and document accepted risks.
