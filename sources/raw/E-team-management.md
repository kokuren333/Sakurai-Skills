桜井政博のゲーム開発原則：チーム運営編

本ドキュメントは、桜井政博氏が自身のYouTubeチャンネルで語った「チーム運営」に関する知見を、AIコーディングエージェントおよびゲーム開発チームが直接適用可能なスキル・原則として再構成したものです。

1. 情報共有とコミュニケーション

【TM-001】日報と『きょうの一枚』による日常的・視覚的な情報共有

  - 原則: 開発進捗や考察を日報に記録し、開発中の最新スクリーンショットを1日1枚共有してチームの視覚的同期を図る。
  - 背景と意図:
    大型タイトルでは数百人が関わるため、末端の作業者が「自分は何のためにこのパーツを作っているのか」を見失い、強いストレスを抱えます。桜井氏は毎日1枚、開発中の画面を『きょうの一枚』として日報に掲載し、進捗や雑感を発信し続けました。画像があることで自発的な閲覧が促され、スタッフ同士のコミュニケーションの場となりました。
  - AIエージェントへの適用:
      - agent_trigger: デイリータスク終了時やPRマージ時。
      - agent_actions: 最新ビルドの動作画面キャプチャを自動取得し、3〜5行の要約ログと共に共有チャンネルへ投稿する。

【TM-002】不満・違和感の即時表明と『ダメ出し＋改善案』のセット提示

  - 原則: 問題に気づいたら後出しせずその場で表明し、ダメ出しには必ず具体的な改善案をセットで添える。
  - 背景と意図:
    プロジェクト終了後に「実は最初からダメだと思っていた」と発言する“後出し”は、発言者の自尊心が満たされるだけで現場には百害あって一利もありません。開発中であれば修正が可能です。「文句を言うな」ではなく、「気づいた瞬間に、改善案とセットで俎上に載せよ」というのが桜井氏の徹底したスタンスです。
  - AIエージェントへの適用:
      - agent_trigger: コードレビュー、設計レビュー時。
      - agent_actions: 批判・警告を出力する際、必ず代替実装コードまたはパラメータ変更案を併記する。

【TM-004】関係職種全員同席による監修と意図の全体共有

  - 原則: 仕様や表現の監修・指示出しは、プランナー経由の伝言ゲームにせず、関係する全職種を同席させて大画面で直接行う。
  - 背景と意図:
    『新・光神話パルテナの鏡』において、ディレクターの指示が企画・プログラマーを経由する中で意図が脱落し、180度違うものが上がってきた苦い経験に基づきます。『スマブラfor/SP』では、広場の大画面に関係者30〜50人（モーション、モデル、コード、エフェクト、サウンド）を集め、全員の前で同時にチェックと修正指示を行いました。これにより伝言ミスが根絶され、他人のチェックを見ることが全員の教材となりました。
  - AIエージェントへの適用:
      - agent_trigger: コア機能の仕様策定・PRレビュー時。
      - agent_actions:
        修正指示を個別モジュールに閉じるのではなく、関係する全サブシステムのエージェント/担当者をコンテキストに含め、「なぜその修正が必要なのか」のデザイン意図を明記する。

2. 組織設計と進行管理

【TM-003】10人チームは7人分：組織拡大に伴う管理コストの織り込みと視座の引き上げ

  - 原則: チーム規模拡大時にはマネジメント工数による実効作業量の目減りを織り込み、定期発表会で作業者の視座を俯瞰へと引き上げる。
  - 背景と意図:
    開発者が10人集まっても、10人分の制作量にはならず約7人分に落ちます。人材管理、スケジュール調整、ルール遵守、機材調達といった「マネジメント業務」が必然的に発生するためです。また、優秀な職人がリーダーになると自身の制作物が作れなくなります。桜井氏は数ヶ月に一度の「プロジェクト発表会」を開き、各班に成果をプレゼンさせることで、製造的な狭い視野からプロジェクト全体を俯瞰する視座へと引き上げました。
  - AIエージェントへの適用:
      - agent_trigger: スケジュール見積もり、マイルストーン策定時。
      - agent_actions: 実効稼働率を70%として見積もりバッファを確保し、定期的な統合デモ検証フェーズをスケジュールに組み込む。

【TM-006】監修依頼の即日返答とディレクターの『ノー監修集中タイム』確保

  - 原則: チームからの監修依頼メールはその日のうちにすべて返し切り、自身の集中作業時間はスケジュールを区切ってブロックする。
  - 背景と意図:
    キーマンの判断が滞ると、チーム全体の作業がストップします。桜井氏は大量に届く監修依頼メールを「その日のうちに返し切る」ことをモットーとしました。一方で、常にメール対応に追われると自身のディレクションや執筆が進まないため、午前中などを「ノー監修タイム」として設定し、集中時間を確保することを推奨しています。
  - AIエージェントへの適用:
      - agent_trigger: レビューキューのトリアージ時。
      - agent_actions: 依存関係の根幹にあるブロックタスクを最優先で即日判定し、自律的推論時間（Deep
        Work）とリクエスト応答時間を分離してスケジューリングする。

【TM-007】議論を持ち帰らずその場で即決・即答する決断主義

  - 原則: 会議で議論を持ち帰ることを原則禁止し、判断者がその場にいるなら即決・即答してプロジェクトの軌道を即座に進める。
  - 背景と意図:
    会議で意見が割れた際に「持ち帰って検討」とすると、案件が宙に浮き、再会議の時間も浪費されます。判断権を持つ者が同席しているなら、その場で即決すべきです。間違っていたなら後から再判断して軌道修正すればよく、細かく素早く再判断を繰り返す方が、結果として正しく最短でゴールに到達できます。
  - AIエージェントへの適用:
      - agent_trigger: 設計方針の決定、コンフリクト調停時。
      - agent_actions: 判断材料が揃った可逆的な決定であれば即座に方針を確定させ、保留タスクを作らない。

3. ディレクションと役割分担

【TM-009】ディレクターとプロデューサーの責務分離（品質と経営の牽制関係）

  - 原則: ディレクターは作品の面白さと品質決定に全責任を負い、プロデューサーは予算・進行・体制・広報を担当して相互に役割を分担する。
  - 背景と意図:
    一般には混同されがちですが、ディレクターは「監督（作品内容の全決定）」、プロデューサーは「マネジメント（資金、座組み、広報、会社折衝）」です。通常ディレクターは1作品にかかりきりになりますが、プロデューサーは複数ラインを兼任します。両者が互いの領域を尊重し、健全に牽制し合うことで、予算を守りつつ最高品質を目指す体制が成立します。
  - AIエージェントへの適用:
      - agent_trigger: 機能追加の提案、スコープ変更時。
      - agent_actions:
        「面白さ・品質への影響（ディレクター目線）」と「コスト・納期・リスクへの影響（プロデューサー目線）」を明確に分離して評価レポートを作成する。

【TM-010】ディレクターの本質は『切る仕事』：無駄の早期切除と軌道修正

  - 原則: ディレクターは機能を作るだけでなく、納期・工数・ハード限界を見越して重すぎる荷物を迅速に切り捨てる決断を下す。
  - 背景と意図:
    ディレクションとは方向を定めることですが、現実はマシンスペックの限界、納期の遅延、工数膨張などのトラブルが頻発します。船を沈没させないために、被害を見越して「重すぎる荷物や燃えそうな荷物を捨てる（デ・スコープする）」ことこそがディレクターの責務です。最悪なのは、ズルズル引き延ばした末にマスター直前で「できませんでした」となることです。
  - AIエージェントへの適用:
      - agent_trigger: フレームレート低下、納期逼迫、メモリ超過の検知時。
      - agent_actions:
        優先度の低い周辺機能やリッチすぎるエフェクトを特定し、オミット（削除）または簡易実装へ差し替えるパッチを即座に作成する。

4. 品質管理とテストプレイ

【TM-005】天文学的組み合わせを前提としたチケット駆動・ランク別デバッグ体制

  - 原則: 昨今のゲームのバグ完全撲滅は不可能であることを前提とし、チケット管理によるタスク喪失防止と深刻度ランク付けで迅速に処理する。
  - 背景と意図:
    『スマブラSP』では89体のファイターの組み合わせだけで約8000通り、技やアイテム、ステージギミックを掛け合わせると天文学的なパターン数になり、完全なデバッグは不可能です。「バグをゼロにしろ」と精神論を振りかざすのではなく、見つかったバグを確実にチケット化し、ランク（S:
    クラッシュ/セーブ破損、A: 進行不能、B/C: 表示等の軽微）をつけて担当職種に割り振り、再テストを経て完了させる組織体制が不可欠です。
  - AIエージェントへの適用:
      - agent_trigger: テスト失敗、クラッシュレポート検知時。
      - agent_actions: 最小再現手順を特定し、深刻度ランクを自動判定して担当モジュールへIssueを起票・追跡する。

【TM-008】対戦バランス調整における専任モニター制と個性の維持

  - 原則: 対戦バランスはプレイ時間の長い専任モニターの膨大な対戦分析に基づき、極端な弱体化を避けて個性を生かした調整を行う。
  - 背景と意図:
    開発者の主観や腕前だけで対戦バランスを調整するのは不可能です。『スマブラSP』では専任モニター班が日々対戦を重ね、その分析データを元に勝率47%〜51%台の均一性を目指しました。しかし、数値を平坦にしすぎるとゲームがつまらなくなります。桜井氏は「個性が殺されそうになった時」に介入し、弱点や隙を増やすことで対抗手段を作り、強みである尖った個性（足の速さ、一撃の重さ）を残す調整を徹底しました。
  - AIエージェントへの適用:
      - agent_trigger: パラメータ調整、メタゲーム分析時。
      - agent_actions:
        勝率データに基づいてバランスを取る際、最強パラメータを直接削るのではなく、クールダウンや硬直フレームを調整して非対称な個性を温存する案を作成する。

【TM-011】ターゲット層（子ども等）による先入観ゼロのモニター観察

  - 原則: ゲームに擦れていないピュアなプレイヤー（子ども等）にテストプレイさせ、意見を聞くのではなくその生の反応と空気感を観察する。
  - 背景と意図:
    初代スマブラ開発時、スタッフの子どもたちを集めてお菓子を用意し、自由に遊ばせる「小学生モニター」を実施しました。ファルコンパンチが決まった瞬間に子どもたちが大絶叫した光景を見て、桜井氏はゲームの根源的な快感を確信しました。知識や先入観のないピュアなプレイヤーが「どこで迷い、どこで飽き、どこで熱狂するか」を言葉ではなく表情や手の止まり方で観察することが、最高のUX改善につながります。
  - AIエージェントへの適用:
      - agent_trigger: チュートリアルや導入シークエンスの設計時。
      - agent_actions: 操作説明を読まない前提の探索型ボットを走らせ、プレイヤーが直感的に誘導されないデッドロック箇所を検出・是正する。
