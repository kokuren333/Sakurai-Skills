      - 補足・解釈 (C): IDEやエンジンのプロジェクトビューにおける探索コスト削減と、スクリプトによる一括正規表現マッチングの精度向上に直結する。
  - 推奨アクション:

  - アンチパターン: HiAttack4（方向が先頭）、Yumi_Shot（ローマ字）、Atk_p1（過度な短縮で意味不明）。

      - 一般化された設計原則 (B):
        ゲームの試行錯誤速度は、パラメーター書き換えから実機反映までのレイテンシに比例する。プログラマーの工数を介さずに調整が完結するパイプラインを構築する。

  - 推奨アクション:
    1.  移動速度、攻撃力、硬直Fなどをコードから外部ファイル（CSV/JSON/ScriptableObject）へ完全抽出する。
    2.  実行中のゲームを再起動・再ビルドすることなく、外部データの変更を即座にリロードする仕組みを作る。
    3.  めったに触らない高度なパラメーターは折りたたみ（Advanced設定）にして誤操作を防ぐ。
  - アンチパターン: スクリプト内の関数に speed = 12.5f などのマジックナンバーを直書きし、数値調整のたびにビルドを走らせる。

原則3: 口語文章＋隅付き括弧【】による仕様書・パラメーター1対1結合作法

  - One Sentence Rule:

  - 背景と解説:
      - 桜井氏の説明 (A):

      - 一般化された設計原則 (B):
        仕様書の挙動解説文をそのまま設定キー名として自己文書化（Self-documenting）し、プログラマーとプランナー間の認知ギャップを排除する。
      - 補足・解釈 (C): BDD（振る舞い駆動開発）の思想をゲームのパラメーターシートに落とし込んだ手法。
  - 推奨アクション:
    1.  個別アクションの仕様書を書く際、「【[挙動説明]は○】」の構文で記述する。
    2.  パラメーターテーブルの項目名には、仕様書の【】内テキストを完全一致で流し込む。
  - アンチパターン: パラメーターシートに param_val_1 などの抽象名が並び、仕様書のどの挙動に対応しているか照合できない状態。

原則4: チケット駆動による工程の可視化と非同期化（直列化の排除）

  - One Sentence Rule: すべてのタスクをデジタルチケット化して担当と期限を明確にし、上流・下流工程を過度に直列化させずに並行進行させよ。
  - 背景と解説:
      - 桜井氏の説明 (A):

      - 一般化された設計原則 (B):

    2.  バグ報告はチケットに集約し、セクションリーダーがトリアージして担当者に割り振る。
  - アンチパターン: モデルが100%完成するまでモーションを一切作らず、モーションができるまでプログラムを書かない完全ウォーターフォール。

原則5: 手触り（ゲームフィール）を評価するための最小物理・入力プロトタイピング

  - One Sentence Rule: 最小限のコードと表示機能を用いて、慣性・速度・応答性などの「手触り」を最優先で検証できる極小プロトタイプを組め。
  - 背景と解説:
      - 桜井氏の説明 (A): 自身の原点である『ファミリーベーシック』は、RAM容量がわずか2KBしかなかったが、スプライト制御（SPRITE,
        DEF
        MOVE）により高速で滑らかな制御が可能だった。自作プログラムでコントローラー入力、慣性力、8方向移動を組む中で、「慣性がどのように操作の手触りに影響を与えるか」を肌で学んだことが『星のカービィ』や『スマブラ』の土台となった。
      - 一般化された設計原則 (B):
        コアメカニクス（移動、加減速、旋回、停止）の気持ち良さは、リッチなグラフィックを載せる前に、最小のオブジェクトとコードで検証・確立しておく。
      - 補足・解釈 (C): ゲームフィール（Game Feel）の初期検証。入力遅延のないレスポンスと、意図的な摩擦・慣性の味付けが重要。
  - 推奨アクション:
    1.  新規アクションの立ち上げ時は、単なる四角形や仮スプライトを用いて、入力と加減速のレスポンスを検証する。
    2.  初速度、最高速度、毎フレームの減速量（摩擦力）を即座に弄りながら、触っていて心地よい数値を探索する。
  - アンチパターン: アニメーションやエフェクトが揃うまで操作性の検証を行わず、後から「動かしていて楽しくない」ことに気づく。

原則6: ふっとばし・被弾リアクションの多層パラメーター分離設計

  - One Sentence Rule:
    ヒット時のリアクション計算を「方向（ベクトル）」「ダメージ比例倍率（影響値）」「基本底上げ値（加算値）」「完全固定値（固定値）」に分解して制御せよ。
  - 背景と解説:
      - 桜井氏の説明 (A):
        『スマブラ』のふっとばしは体力制ではなく場外落下制のため独自仕様。構成要素は①ベクトル（全方位設定、攻撃者の移動に沿わせる補正含む）、②リアクション影響値（ダメージ比例倍率）、③リアクション加算値（無条件の底上げ値）、④リアクション固定値（ダメージ不問の完全固定）。連続攻撃の途中段を固定値にすることで相手の抜けを防ぎ、最終段のみ影響値で大きくふっとばす。
      - 一般化された設計原則 (B):
        ノックバックや怯みリアクションを単一の「力」で処理せず、「蓄積状況でスケールする要素」と「コンボを成立させるための固定拘束要素」を直交させて定義する。
      - 補足・解釈 (C): 多段攻撃における「すっぽ抜け」を数理的に防止するための設計パターン。
  - 推奨アクション:
    1.  ヒット判定データに Vector, ReactionScaling（影響値）, ReactionBase（加算値）,
        FixedReaction（固定値） を持たせる。
    2.  連続ヒット技の途中段には FixedReaction を設定し、最終段のみ ReactionScaling を設定する。
    3.  移動しながら当てる技には、攻撃側の進行方向にノックバックベクトルを一定割合引っ張る補正を入れる。
  - アンチパターン: 全段をダメージ比例ふっとばしにした結果、相手が高ダメージの時に多段技の2発目で吹き飛んでしまい、肝心のフィニッシュが当たらない。

原則7: 多人数分散開発におけるファイル排他制御と「先祖返り」自動検知

  - One Sentence Rule:
    アセット管理ツールで編集権限（ロック/マージ）を厳密化し、更新上書きによる「先祖返り（過去バージョンへの逆戻り）」を防止せよ。
  - 背景と解説:
      - 桜井氏の説明 (A):
        多人数開発ではファイルをサーバー上で管理し、編集時のロックと解除を行う。二重編集時はマージを試みるが、手動修正が必要になることもある。理屈上は回るはずだが、現場では他人の変更が消えて古い状態に戻る「先祖返り」が頻発する。バックアップを保持し、異変に即座に気づける体制が必要。
      - 一般化された設計原則 (B): バイナリアセットなど自動マージ不能なファイルには排他的ロック（Exclusive
        Checkout）を強制し、マージミスによる過去リビジョンへの巻き戻りを防ぐ。
      - 補足・解釈 (C): Git LFSのロック機能やPerforceの排他制御、およびマージ時の差分目視確認プロトコル。
  - 推奨アクション:
    1.  シーン、プレハブ、3Dモデルなどのバイナリファイルは、チェックアウト時に排他ロックをかける設定にする。
    2.  マージコンフリクト解決時、ツール任せにせず、直近コミット履歴と差分（Diff）を目視確認する。
  - アンチパターン: バイナリファイルを複数人で同時編集し、後からコミットした側が前者の修正内容を完全に消去（先祖返り）させる。

  - One Sentence Rule: デバッグ機能は専用機材を要求せず、プレイ用の単一コントローラー（同時押し等）で全操作が完結するように実装せよ。
